Требования к курсовой работе 

1. Структура
Курсовая работа должна быть снабжена отчетом, который имеет следующую структуру:

Титульный лист
Оглавление
* Постановка задачи
* Алгоритм
* Инструкция пользователя
* Тестовые примеры
Список литературы
2. Пояснения к разделам
2.1. Титульный лист
На титульном листе должно быть:
название учебного заведения
название предмета
тип работы (курсовая)
тема работы
ФИО студента
ФИО преподавателя, который будет проверять работу
дата
2.2. Оглавление
Оглавление должно содержать названия разделов и номера соответствующих страниц. Желательно, что оглавление генерировалось автоматически (необходимо использовать стили).
2.2. Постановка задачи
Должно быть описано задание на курсовую работу ("Задачей данной курсовой работы является разработка программы, которая..."). 
Должна быть приведена информация, позволяющая понять постановку задачи. Пример: для задачи коммивояжера должно быть описано, какими свойствами должен обладать маршрут, который мы ищем.
Должна быть ссылка на книгу из списка литературы, в которой описана задача курсовой.
Должны быть приведены примеры, которые показывают, что задача имеет смысл. Примеры: для задачи коммивояжера на небольшом примере необходимо показать, что есть разные отличающиеся по стоимости маршруты. При описании примера рекомендуется использовать рисунки.
2.3. Алгоритм
Должно быть описано, на каких идеях построен алгоритм. 
Должно быть приведено подробное описание алгоритма и структур данных, которые он использует. Шаги алгоритма должны быть проиллюстрированы рисунками.
Должно быть показано пошаговое выполнение алгоритма на простом примере.
Если алгоритм взят из книги/сайта, то должна быть приведена ссылка на этот источник.
Должен быть приведен псевдокод алгоритма. Псевдокод --- это код на языке C++, в котором непринципиальные шаги заменены фразами на русском языке. Пример того, что можно заменить: вывод результатов, ввод исходных данных, копирование из одного массива в другой и т.д. 
На основе псевдокода должен быть проведен анализ сложности алгоритма в терминах O(n).
2.4. Инструкция пользователя
Должно быть описано, как запускать программу. Пример: параметры командной строки.
Должен быть описан формат входного файла. 
Должен быть описан формат выходного файла.
2.5. Тестовые примеры
Должны быть приведены 3 тестовых примера (три входных и выходных файла), по которым можно проверить корректность работы программы.
2.6. Список литературы
Должен содержаться список источников (книги, статьи, сайты, методички), которые были использованы при подготовке курсовой. На все источники должны ссылки из текста отчета. 
Про книгу должны быть указано:
название
авторы
издательство 
год
Про сайт должно быть указано:
тема
ссылка
год
3. Требования к оформлению
Необходимо использовать стили. Одинаковые элементы документа (заголовки, списки, основной текст в разных разделах) оформляются однотипно.
Должен быть отдельный стиль для псевдокода с моноширинным шрифтом.
На все рисунки, таблицы и источники должны быть ссылки из текста. Ссылка должна быть “автоматической”: на нее можно нажать и перейти туда, куда она ссылается. 
У всех рисунков и таблиц должны быть подписи (например, Рисунок 1 - Название). Ко всем рисункам и таблицам нужны пояснения в тексте.
Наиболее предпочтительной формой изложения является безличная: “будет рассмотрено”, “предложен алгоритм”, “сложность вычисляется как”. Изложение от первого лица недопустимо: “я написал программу, которая”, “ниже я привел пример”.
Необходимо две версии в Word и TeX.
4. Требования к исходному коду
Общие требования:
Программа должна получать параметры через командную строку
Вместе с исходным кодом необходимо включать тестовые примеры (см. 2.5. Тестовые примеры).
Программа должна состоять как минимум из трех файлов. Пример: main.cpp, salesman.cpp, salesman.h
Программа должна содержать main и еще как минимум 3 функции (метода): загрузка исходных данных, алгоритм, сохранение результата.
Программа должна быть написана с использованием библиотеки STL.
Необходимо наличие документации, подготовленной с помощью doxygen.
Боритесь с дублированием кода: это самое большое возможное зло. Если в процессе написания вам понадобилось копировать и вставить кусок своего кода в этот же код, то это первый признак того, что происходит дублирование. Постарайтесь детектировать идентичные и похожие места, вынесите общую часть в отдельную функцию или класс и воспользуйтесь ей дважды с разными аргументами.
Старайтесь писать аккуратно. Удаляйте лишний, неиспользуемый, закомментированный код, удаляйте переменные и функции, которые вам на самом деле не нужны, остальные называйте понятно.
На код должно быть приятно смотреть, его должно быть легко читать. Вы его пишете один раз, сохраняете, после чего его читают много раз, поэтому выгодно потратить при написании немного времени на приведение кода в порядок, чтобы впоследствии сократить своё и чужое время на чтение

Абсолютно правильного одного стиля нет. Люди обычно в начале проекта просто о чем-то договариваются. Ниже приведен минимальный набор правил, которые встречаются в большинстве "договоров". Рекомендации по стилю:
Использование глобальных переменных недопустимо.
Файлы имеют осмысленные имена (например, src.cpp и header.h недопустимо). Файл с исходный текстом и соответствующий заголовочный файл имеют одинаковые имена (dfs.h, dfs.cpp). Имя файла похоже на имя класса, который описан в этом файле (vector.h и vector.cpp, class vector)
man.cpp, criss_cross.cpp, criss_cross.h
В рамках одного проекта (например, курсовой) у всех файлов стиль один
Лучше не жалеть пробелов
int a = b + c;
f(4, 5, "fdfdffdf");
У вложенных конструкций должны быть отступы
for(...) {
    if(...) {
    }
}
Лучше не жалеть пустых строк
void f() {
    for( ...) {
    }

    if(...) {
    }
}

void g() {
    int b = 5 + 6;
}

Перед отправкой на проверку желательно убрать все временно закомментированные участки кода.
Имена:
Должны быть осмысленные имена у переменных и функций.
Желательно, чтобы имена функций начинались с глагола.
Несколько слов в составе идентификатора лучше разделить (getNextPacket или get_next_packet неважно, главное, чтобы везде одинаково).
Минимум сокращений (idx ---> index). Счетчиков в цикле это не касается.
Транслитерация с русского языка в именах переменных и функций не приветствуется (massive, stroka --- отказать :)
